1. React: ciclo de vida e useEffect

Todo componente passa por 3 fases. Em funcionais, tudo fica no useEffect.

FaseClasseHookUso
MontagemcomponentDidMountuseEffect(fn, [])Buscar dados iniciais
AtualizaçãocomponentDidUpdateuseEffect(fn, [valor])Refazer busca quando filtro muda
DesmontagemcomponentWillUnmountreturn () => {…}Cancelar timer/listener/requisição
  • []: roda 1 vez, após o primeiro render (nada muda, nunca fica “desatualizado”).
  • [valor]: roda na montagem e sempre que valor mudar.
  • Array de dependências: tudo que o efeito usa de fora (props, estado, funções). O ESLint (eslint-plugin-react-hooks) avisa se faltar.
  • Loop infinito: efeito faz setState do mesmo valor listado nas dependências.
  • A limpeza roda na desmontagem e também antes de cada nova execução do efeito.
  • Em classes, uma lógica (assinar/remover evento) ficava espalhada em 2 métodos; hooks juntam tudo.
useEffect(() => {
  const id = setInterval(() => setHora(new Date()), 1000);
  return () => clearInterval(id); // evita setState em componente que saiu
}, []);

2. HTTP, Axios e JSON-Server

Métodos e status

MétodoIntenção
GETBuscar, sem alterar
POSTCriar
PUTSubstituir por completo
PATCHAtualizar parcialmente
DELETERemover

2xx sucesso (200 OK, 201 Created) · 4xx erro do cliente (400, 401, 404) · 5xx erro do servidor (500). Requisições são assíncronas (Promise, .then/.catch, async/await) e os dados vêm em JSON.

Axios x fetch

  • Axios já entrega o JSON em resposta.data (fetch exige .json()).
  • Erros 4xx/5xx caem direto no .catch() (no fetch não).
  • axios.create() cria instância com baseURL fixa. Instalar: npm install axios.
  • POST: 2º argumento é um objeto JS comum, sem JSON.stringify.
// src/services/api.js
import axios from 'axios';
const api = axios.create({ baseURL: import.meta.env.VITE_API_URL });
export default api;

// no componente
useEffect(() => {
  api.get('/usuarios').then(r => setUsuarios(r.data))
    .catch(console.error).finally(() => setCarregando(false));
}, []);

Variáveis de ambiente (Vite)

  • Só variáveis com prefixo VITE_ vão ao navegador (segurança). Lidas via import.meta.env.
  • .env (todos), .env.development (npm run dev), .env.production (npm run build).
  • .env no .gitignore; versionar um .env.example só com as chaves.

JSON Server (mock)

Mock = versão falsa do servidor para o front não ficar bloqueado. O db.json vira API REST: cada chave de topo é uma coleção.

npx json-server@0 db.json -p 8080 -w
  • -p 8080 porta · -w watch (reinicia ao salvar) · @0 fixa a versão 0.x (a 1.x mudou formato das respostas e exige config extra).
  • Rotas: GET /usuarios, GET /usuarios/1, POST /usuarios, PUT /usuarios/1, DELETE /usuarios/1.
  • Ligar: VITE_API_URL=http://localhost:8080. Quando a API real ficar pronta, só troca a variável.

3. LLMs

  • LLM (Large Language Model): modelo deep learning treinado com enormes quantidades de dados; máquina de predição estatística que prevê a próxima palavra.
  • Modelo aprende de exemplos · Deep learning = redes neurais com muitas camadas · Large = bilhões de parâmetros · Predição = calcula a chance de cada palavra seguinte.
  • Consequência: gera o texto mais plausível, não necessariamente o verdadeiro → alucinação.
  • Word vector: cada palavra vira um ponto em espaço de centenas/milhares de dimensões (analogia: lat/long). Perto = uso parecido. Direções carregam relações: rei − homem + mulher ≈ rainha. As dimensões não têm nome.
  • Caminho: texto → tokens → IDs → vetores. Token = pedaço de texto (palavra, parte ou pontuação).
  • Treino: vetores começam aleatórios; ciclo prever → medir erro → ajustar, bilhões de vezes. Ajusta todos os parâmetros. É a parte cara. Depois, o modelo não aprende sozinho: a conversa não altera os números internos.
  • Transformer: atenção, cada palavra “olha” as vizinhas (banco da praça × banco de dinheiro). A saída é lista de probabilidades; escolhe entre as mais prováveis com um pouco de aleatoriedade (por isso respostas diferentes).

O que muda de um modelo para outro

  • Modalidade (texto, imagem, áudio, vídeo; multimodais) · Tamanho (maior = mais capaz, lento, caro) · Janela de contexto (quanto lê de uma vez) · Data de corte (fim dos dados de treino; depois só com ferramentas) · Acesso (proprietário via API/produto; aberto roda na sua máquina).
Modelo é o motor; produto é o carro. ChatGPT, Claude Code e app do Gemini são produtos. Não existe “o melhor modelo”: existe o adequado a custo, velocidade e qualidade.

4. Tools, RAG e MCP

  • AI Tools: funções, APIs, apps que o modelo usa para tarefas além da capacidade nativa (ex.: hora atual, clima, banco de dados, arquivos). Têm descrição, parâmetros e resultado esperado. O modelo decide sozinho se faz uma tool call.

Anatomia: 1) app envia pergunta + lista de tools → 2) modelo devolve pedido (nome + parâmetros) → 3) a aplicação executa a função e controla permissões → 4) resultado volta ao modelo como texto → 5) modelo escreve a resposta. Cada ida e volta é uma chamada ao modelo: custa tempo e tokens.

Tipos: execução de código, APIs, documentos, busca (web, RAG), geolocalização, agenda, e-commerce.

  • RAG (geração aumentada por recuperação): pergunta → busca → trechos → resposta. Forma mais comum de responder sobre conteúdo que não estava no treino.
  • MCP (Model Context Protocol): protocolo padrão, a “tomada universal”: a tool é escrita uma vez e várias aplicações usam. No Foundry aparece como “servidores MCP”.

5. Agentes, Skills e Multi-agentes

AssistenteAgente
Decisão / iniciativaReage a prompts, não decideToma iniciativa e decide quais ações
PlanejamentoNão tem; interação a cada etapaPlaneja, observa a resposta, separa em etapas
FocoResponder (chat)Resultados (objetivos)
ExemplosClaude AI, ChatGPT, GeminiClaude Code, GitHub Copilot, Antigravity

Agente = LLM (cérebro) + Tools (mãos) + Objetivo + Ciclo (repetir até terminar). Sem o ciclo, sobra um assistente com ferramentas. Assistente = estagiário (você dita cada passo); agente = profissional experiente (você dá o objetivo). Um produto pode ser os dois (ex.: Copilot).

Componentes: percepção/processamento · pensamento e decisão · planejamento · ação · memória (curto prazo = histórico da tarefa; longo prazo = anotações; o modelo não é retreinado) · aprendizado/adaptação (mudar a rota).

  • ReAct: pensa → age → observa → repete. Flexível, replaneja na hora, porém mais lento/custoso (relê histórico que só cresce). Bom para tarefas imprevisíveis.
  • ReWOO: Planner → Worker (tools) → Solver. Poucas chamadas, menos tokens, mas o plano não se ajusta sozinho. Bom para tarefas previsíveis. Na prática, mistura-se os dois.

Skills

  • Conjunto de instruções, scripts e/ou recursos que o agente carrega dinamicamente; a “receita de bolo”. Não executa ações por si só, apenas orienta.
  • Ganho: experiência vira instrução, atualiza o que o modelo sabe. Exemplo da aula: 25% → 95% de acerto com skills (mesmo agente/modelo). Muitas vezes o salto vem de explicar melhor a tarefa.
  • Cuidado: skill de terceiros é instrução que seu agente vai obedecer, com acesso às suas ferramentas: leia antes de instalar. Formato SKILL.md.

Multi-agentes

  • Um orquestrador delega a agentes especialistas. Ganhos: foco (4 tools decidem melhor que 40), contexto limpo, paralelismo. Preço: mais custo (mais chamadas) e mais coordenação.
  • Regra prática: comece com um agente; divida se tarefas independentes, tools demais ou paralelismo compensar.

6. Azure for Students, Foundry e OpenCode

  • Azure for Students: benefício gratuito, US$ 100 de crédito, sem cartão. Ativar em azure.microsoft.com/pt-br/free/students com e-mail @sptech.school, verificação acadêmica, telefone próprio, CNPJ em branco, endereço da faculdade, marcar só a 1ª caixa de termos.
  • Microsoft Foundry (antigo Azure AI Foundry): plataforma para criar, publicar e governar agentes. +10.000 modelos, tools/MCP compartilhadas, observabilidade. Concorrentes: Amazon Bedrock, Vertex AI Agent Builder, watsonx Orchestrate, Agentforce.
  • OpenCode: agente de código open source (MIT), independente de modelo, 75+ provedores. Não é um LLM: fornece tools e o loop do agente. Instruções do projeto em AGENTS.md. Similares: Claude Code, Codex CLI, Gemini CLI, Cursor, Cline, Aider.

Passo a passo

Foundry: criar recurso (guarde o nome, entra na URL) → Go to Foundry portal → Compilação → escolher modelo → Implantar (Configurações padrão) → status Succeeded → em Detalhes copiar Ponto de extremidade + Chave. Prefira modelos leves (ex.: gpt-5.1-codex-mini); nem todo modelo está disponível (região/cota).

OpenCode: npm install -g opencode-ai → opencode → /connect → provedor Azure (≠ Azure Cognitive Services) → método API key → nome do recurso → colar a chave → escolher modelo → “Hello AI”. Trocar modelo: /models. Config por arquivo: ~/.config/opencode/opencode.json; guarde a chave com opencode auth login e nunca comite a API key.
